## Summary and actual behavior

**Reproduced.** [db.rs:460](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/crates/omera-storage/src/db.rs#L460) returns `last_insert_rowid()` after an UPSERT. Insert A, insert B, then upsert A: the returned ID is B's although A's row was updated. Pipeline harvesting uses that return value for `enqueue_cleanup`.

## Environment and evidence

- Baseline: Omera 0.4.3, `dev` at [`bdac8fb`](https://github.com/BerryUIKI/Omera/commit/bdac8fbcdbac5535075e091453b77c3afe518ba5); SQLite schema 15.
- Review host: Windows; the inspected application was launched from the repository root with `pnpm run tauri dev`.
- Evidence strength is stated above. For code-confirmed scenarios, the steps below describe a targeted validation scenario rather than a completed end-to-end reproduction. Remote-provider, destructive real-library and cross-platform scenarios were not exercised.

## Reproduction or validation scenario

1. Create an in-memory database and insert two synthetic file records A and B with different paths.
2. Call `upsert_file` again for A after inserting B.
3. Assert the returned ID equals A's ID; the current implementation returns B's ID.

## Expected behavior

Every upsert returns the ID of the row it actually inserted or updated.

## Acceptance criteria

- [ ] Return the affected row ID using `RETURNING` or a verified transactional lookup.
- [ ] Test updates after intervening inserts and multiple conflicting upserts.
- [ ] Verify cleanup, tag and album callers attach work to the correct returned ID.
