## Summary and actual behavior

**Code-confirmed.** `auto_backup_enabled` and `auto_backup_interval_days` occur in configuration models/defaults and settings load/save, but there is no execution path that schedules a snapshot from them. The Rust default enables this field, while frontend defaults disable it. The settings component holds and serializes these values but does not render an automatic-backup control. This is an incomplete configuration/feature contract, not an observed enabled GUI toggle that falsely reports protection.

Source: [domain configuration/defaults](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/crates/omera-domain/src/cloud_backup.rs#L50), [Settings serialization](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/src/components/SettingsModal.vue#L212).

## Environment and evidence

- Baseline: Omera 0.4.3, `dev` at [`bdac8fb`](https://github.com/BerryUIKI/Omera/commit/bdac8fbcdbac5535075e091453b77c3afe518ba5); SQLite schema 15.
- Review host: Windows; the inspected application was launched from the repository root with `pnpm run tauri dev`.
- Evidence strength is stated above. For code-confirmed scenarios, the steps below describe a targeted validation scenario rather than a completed end-to-end reproduction. Remote-provider, destructive real-library and cross-platform scenarios were not exercised.

## Expected behavior

Automatic-backup configuration has a consistent, documented capability contract and is exposed only when scheduling works.

## Acceptance criteria

- [ ] Implement persisted due times, successful-backup state, catch-up and retry, or consistently mark scheduling unavailable.
- [ ] Align frontend/backend defaults and avoid implying active protection from an inert field.
- [ ] Before adding a control, verify snapshot creation at a shortened interval and restart/failure recovery.
