## Summary and actual behavior

**Reproduced.** [history.ts:45](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/src/utils/history.ts#L45) pops before awaiting undo; redo does the same. A rejected IPC operation leaves the command in neither stack. Both rejection probes fail; existing tests cover only successful sequential operations.

The class also lacks an in-flight guard/serialization contract.

## Environment and evidence

- Baseline: Omera 0.4.3, `dev` at [`bdac8fb`](https://github.com/BerryUIKI/Omera/commit/bdac8fbcdbac5535075e091453b77c3afe518ba5); SQLite schema 15.
- Review host: Windows; the inspected application was launched from the repository root with `pnpm run tauri dev`.
- Evidence strength is stated above. For code-confirmed scenarios, the steps below describe a targeted validation scenario rather than a completed end-to-end reproduction. Remote-provider, destructive real-library and cross-platform scenarios were not exercised.

## Reproduction or validation scenario

1. Create `ActionHistory` and execute a command whose `undo` rejects.
2. Catch the rejection and check `canUndo()`; it becomes false.
3. Repeat with a successful undo followed by a rejecting redo; `canRedo()` becomes false.

## Expected behavior

Failed history operations retain a retryable command and cannot race with another transition.

## Acceptance criteria

- [ ] Move commands between stacks only after confirmed success and retain them on rejection.
- [ ] Serialize or guard in-flight execute/undo/redo operations.
- [ ] Test failed IPC, rapid shortcuts, out-of-order completion and explicitly defined partial-success handling.
