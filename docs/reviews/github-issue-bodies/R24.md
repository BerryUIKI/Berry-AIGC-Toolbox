## Summary and actual behavior

**Code-confirmed.** [cloud_sync.rs:527](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/src-tauri/src/cloud_sync.rs#L527) reads each entire media file into memory; concurrency permits up to 16 workers. Sixteen large videos can create many gigabytes of allocations. SHA mode may read once for hashing and again for upload. The limiter at [cloud_sync.rs:49](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/src-tauri/src/cloud_sync.rs#L49) sleeps for the whole file's allowance while holding the shared limiter lock; cancellation is not checked during that sleep or the transfer.

## Environment and evidence

- Baseline: Omera 0.4.3, `dev` at [`bdac8fb`](https://github.com/BerryUIKI/Omera/commit/bdac8fbcdbac5535075e091453b77c3afe518ba5); SQLite schema 15.
- Review host: Windows; the inspected application was launched from the repository root with `pnpm run tauri dev`.
- Evidence strength is stated above. For code-confirmed scenarios, the steps below describe a targeted validation scenario rather than a completed end-to-end reproduction. Remote-provider, destructive real-library and cross-platform scenarios were not exercised.

## Reproduction or validation scenario

1. Review worker allocation and rate limiting with several large synthetic files and concurrency 16.
2. Use a slow local endpoint or injected transport to exercise hashing/upload waits.
3. Cancel during throttling/transfer and measure allocation and cancellation latency.

## Expected behavior

Memory has a bounded global byte budget and cancellation interrupts chunk transfer and throttling promptly.

## Acceptance criteria

- [ ] Stream hashing and upload in bounded chunks and avoid redundant whole-file reads.
- [ ] Enforce a global memory budget independent of worker count/file size.
- [ ] Make limiter waits/transfers interruptible and measure peak memory/cancel latency using synthetic files.
