## Summary and actual behavior

**Code-confirmed.** [commands.rs:1793](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/src-tauri/src/commands.rs#L1793) holds the shared `AppState.db` guard over the entire batch decode/encode/archive job. [commands.rs:1777](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/src-tauri/src/commands.rs#L1777) holds it during an export estimate's image processing. Moving the operation into `spawn_blocking` does not release that mutex; library reads and mutations using it must wait behind the job.

## Environment and evidence

- Baseline: Omera 0.4.3, `dev` at [`bdac8fb`](https://github.com/BerryUIKI/Omera/commit/bdac8fbcdbac5535075e091453b77c3afe518ba5); SQLite schema 15.
- Review host: Windows; the inspected application was launched from the repository root with `pnpm run tauri dev`.
- Evidence strength is stated above. For code-confirmed scenarios, the steps below describe a targeted validation scenario rather than a completed end-to-end reproduction. Remote-provider, destructive real-library and cross-platform scenarios were not exercised.

## Reproduction or validation scenario

1. Trace `transform_library_files_batch` from `db(&state)` through `execute_library_batch_transform`.
2. Inspect `estimate_export_file` while it decodes/encodes an image.
3. Run a slow synthetic transform batch and issue gallery/search reads that use the shared database mutex.

## Expected behavior

CPU/filesystem work runs outside the shared database guard; read latency does not depend on the duration of the whole codec job.

## Acceptance criteria

- [ ] Fetch bounded inputs under short locks and release shared guards before codec/filesystem work.
- [ ] Persist per-item results using short transactions and an explicit connection/worker contract.
- [ ] Measure gallery/search responsiveness during slow batch work; `spawn_blocking` alone is insufficient.
