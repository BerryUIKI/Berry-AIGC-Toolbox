## Summary and actual behavior

**Code-confirmed.** [update_verification.rs:4](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/src-tauri/src/update_verification.rs#L4) requires an embedded Omera/Berry public key, and downloads require adjacent `.minisig` assets. The release workflow does not set either key variable or generate/upload these signature assets. Its macOS code signing/notarization does not supply the separate minisign update mechanism.

The application fails closed without update trust, which is appropriate security behavior. The gap is feature/release readiness: releases built solely by the checked-in workflow cannot complete that automatic-update path.

## Environment and evidence

- Baseline: Omera 0.4.3, `dev` at [`bdac8fb`](https://github.com/BerryUIKI/Omera/commit/bdac8fbcdbac5535075e091453b77c3afe518ba5); SQLite schema 15.
- Review host: Windows; the inspected application was launched from the repository root with `pnpm run tauri dev`.
- Evidence strength is stated above. For code-confirmed scenarios, the steps below describe a targeted validation scenario rather than a completed end-to-end reproduction. Remote-provider, destructive real-library and cross-platform scenarios were not exercised.

1. Build using only the checked-in release workflow and inspect embedded update-key inputs.

3. Trace update verification when neither embedded public key is configured.

## Expected behavior

Published automatic-update artifacts have the required signatures and embedded trust, with a tested install-to-next-version path.
