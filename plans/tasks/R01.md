## Expected behavior

Restore is staged and activated before opening SQLite connections; the current database remains recoverable on failure.

## Recommended implementation

1. Route cloud restore through the staged recovery lifecycle: validate archive/database integrity, schema and foreign keys; create a consistent rollback snapshot; stage replacement.
2. Quiesce submissions/connections and apply replacement before reopening the database and workers, typically through the established restart flow. Do not overwrite a live mmap/WAL database or ignore rollback errors.

## Evidence and source pointers

**Reproduced and code-confirmed.** [cloud_backup.rs:903](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/src-tauri/src/cloud_backup.rs#L903) makes a raw rollback copy of only the live main database, ignores backup errors, and copies the restored file directly over the active database. [commands.rs:4739](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/src-tauri/src/commands.rs#L4739) calls this while `AppState` and workers still hold database connections; restart occurs only afterward. The database enables a 256 MB mmap at [db.rs:177](https://github.com/BerryUIKI/Omera/blob/bdac8fbcdbac5535075e091453b77c3afe518ba5/crates/omera-storage/src/db.rs#L177).

With a synthetic active WAL connection, this Windows build fails with `Failed to replace live database ... user-mapped section open (os error 1224)`. No real database was restored. On systems allowing the copy, the source path still has active connections/WAL and non-atomic replacement risk; corruption or WAL contamination was not demonstrated on this host. Local restore already uses `recovery::stage_restore`, so cloud restore should use the same lifecycle.
